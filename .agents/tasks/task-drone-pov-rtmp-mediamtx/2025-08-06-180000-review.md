# LetsView removal, MediaMTX WebRTC pipeline, GPS-enabled reporting

This change replaces the LetsView screen-mirroring video pipeline with a direct MediaMTX RTSP/WebRTC architecture, removes all pywin32/Windows dependencies, adds a GPS provider abstraction for post-flight geolocation, adds crack region cropping to the capture pipeline, and extends the database/reporting stack with GPS columns and cropped images. The frontend shows the drone feed via an iframe pointed at MediaMTX's built-in WebRTC player, while the backend continues to consume the RTSP stream through OpenCV for inference. The GPS provider models the DJI Neo 2's limitation (no live GPS via RTMP) by always returning None for live position and supporting post-flight log import with bisect-based timestamp matching.

Watch for: Float-to-int bbox slicing bug in crop code will raise TypeError at runtime (confirmed). Iframe `load` event unreliability for cross-origin MediaMTX pages means the stream monitor may never detect connection (likely). Timezone naivety in GPS timestamp parsing will cause silent mismatch when server is not in UTC (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The LetsView removal is complete — no references remain in source files, the registry drops the entry, detector.py no longer imports or branches on LetsViewSource, and requirements.txt drops pywin32.

The WebRTC integration delegates all media handling to MediaMTX's built-in player page embedded in an iframe. This avoids custom WebRTC signaling code entirely, but means the frontend has no visibility into the stream's actual connection state beyond iframe load events, which are unreliable for cross-origin content.

The GPS provider's bisect-based timestamp matching with configurable tolerance is correct for the stated use case, but timezone naivety in `_parse_timestamp` means `strptime`-parsed naive datetimes get interpreted as local time, while capture timestamps are UTC. GPS log matching will silently return wrong points if the server isn't in UTC.

The crack cropping logic has a confirmed bug: YOLO bounding box coordinates are floats, and the crop code uses them directly as numpy slice indices without casting to int. Every crop attempt silently falls through to the exception handler. Crops are never generated.

## Float bbox and silent crop failures

The bounding box from YOLO inference (`result.boxes.xyxy[i].cpu().numpy().tolist()`) produces a list of Python floats like `[102.4, 55.7, 380.2, 290.1]`. In `capture_manager.py`, the crop code does:

```python
x1, y1, x2, y2 = bbox[0], bbox[1], bbox[2], bbox[3]
bbox_w = x2 - x1  # float
pad_x = int(bbox_w * CROP_PADDING_RATIO)  # int
crop_x1 = max(0, x1 - pad_x)  # float (float - int = float)
...
cropped = raw_frame[crop_y1:crop_y2, crop_x1:crop_x2]  # TypeError
```

Numpy array slicing with float indices raises `TypeError: slice indices must be integers or None or have an __index__ method`. The enclosing `except Exception` catches this silently and sets `crop_path = None`, so the feature appears to work (no crash) but never actually produces a cropped image. The fix: `x1, y1, x2, y2 = int(bbox[0]), int(bbox[1]), int(bbox[2]), int(bbox[3])`.

Once fixed, the bare `except Exception` will continue to swallow any future regression in this block. Adding `logger.warning("Crop failed", exc_info=True)` inside the handler would surface problems without breaking the pipeline.

## Timezone asymmetry in GPS log matching

The GPS provider's `_parse_timestamp` method, when given an ISO string without timezone suffix (e.g. `"2026-08-12T14:32:18.000"`), uses `datetime.strptime` which produces a naive datetime. Calling `.timestamp()` on a naive datetime interprets it as **local time** per Python's documented behavior.

The capture pipeline creates its timestamp with `datetime.now(timezone.utc)`, which is timezone-aware UTC. When this datetime is passed to `get_position_at_timestamp`, it hits the `isinstance(ts, datetime)` branch and correctly converts to UTC epoch seconds.

The mismatch: if a GPS log file contains timestamps without timezone info (common for DJI flight logs), they're parsed as local time. The capture timestamp is UTC. These two epoch values will differ by the server's UTC offset, and GPS matching will silently return the wrong point or no point at all. The fix is to either require GPS log timestamps to include timezone info, or accept a `tz` parameter on `import_gps_log` and apply it during parsing.

## WebRTC iframe stream monitoring

For a cross-origin iframe (MediaMTX on port 8889 vs Flask on 5000), the `load` event fires when the iframe navigation completes, regardless of whether the content is functional. The browser provides no cross-origin visibility into iframe content. The `error` event fires only for network-level failures (DNS, refused connection), not for HTTP errors or empty streams.

If MediaMTX is running but the drone isn't streaming, the iframe loads MediaMTX's player page (showing its own "waiting" state), the `load` event fires, `_streamConnected` becomes true, and the disconnected overlay stays hidden. The user sees MediaMTX's internal UI rather than the app's status message. The existing `/status` endpoint already reports `camera_connected` from the backend's RTSP connection — tying the overlay to that flag would be more reliable than iframe load events.

## Test coverage gaps

No integration test exercises the actual crop path with a real numpy frame and float bounding box. The `test_crop_padding_ratio` test only checks that the constant exists and equals 0.15. A test that performs crop logic with float bbox coordinates would have caught the TypeError immediately.

No test covers timezone-variant timestamps in GPS matching (e.g., feeding a UTC-aware datetime as the query against a log parsed from naive strings). This is where the timezone bug manifests and a test would prevent regressions when the parsing is fixed.

## Residual dead CSS

The `.source-selector` CSS block remains in `style.css` despite the source selector HTML being removed from `dashboard.html`. Dead code — minor cleanup.
