# Research-grade crack detection pipeline with dark-theme frontend

Adds a complete Flask-based UAV crack detection system: a multi-stage auto-capture pipeline with temporal verification and morphological validation, a dark-themed single-page dashboard with alert sound management, an inspections history page with CRUD operations, Windows Graphics Capture integration for LetsView, and frame preprocessing (CLAHE/gamma/sharpening). The system targets a capstone defense demo where false-positive suppression and visual polish matter more than production scale.

Watch for: The `_DB_LOCK` mutex in `inspection_db.py` serializes all database access including reads, creating a single-writer bottleneck that will stall the `/status` polling if a long write (PDF generation + DB insert) is in progress on the capture thread (confirmed). The `validate_cracks` function receives `masks` from `annotate_frame` but indexes them by position (`masks[i]`), which can index-mismatch if the metadata list was filtered or reordered upstream (likely). The LetsView Windows Graphics Capture implementation imports `winsdk` modules inside `read()` on every frame, paying an import-lookup cost per-frame instead of caching at `open()` time (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The capture pipeline is a six-stage state machine running in a background thread. When five consecutive frames over 1.5 seconds exceed the confidence threshold, the system freezes the best frame, validates image quality, re-runs YOLO inference on it, applies morphological crack validation, and saves the result to disk, SQLite, and a PDF report. The shared `_DB_LOCK` that wraps all database operations means any slow write blocks status polling from the Flask request threads.

The crack validator combines geometric filters (area, length, aspect ratio), DJI UI zone rejection, and morphological analysis (erosion/dilation, circularity, solidity). The structural risk is the positional coupling between the `masks` array indices and the `crack_metadata_list` order — if any upstream filtering occurs before calling `validate_cracks`, the mask at index `i` will not correspond to metadata entry `i`.

The frontend fires alert sound and banner only on `analysis_complete` state, which can only be reached after temporal verification, quality validation, re-inference, and crack validation all pass. The 1500ms poll interval means sound fires up to 1.5s after the backend reaches `analysis_complete` — acceptable for a demo, but if sub-second response is needed, a WebSocket push would be required.

The LetsView source re-imports `winsdk.windows.graphics.imaging` inside the `read()` hot path on every frame rather than caching the module reference at `open()` time.

<details>
<summary>Issues (7)</summary>

1. **DB lock serializes reads and writes** — `_DB_LOCK` wraps every `get_inspections`, `get_summary_stats`, and `insert_inspection` call. Move to WAL-mode read concurrency (which is already enabled but unused because the lock prevents concurrent connections) or use a connection-per-thread pool instead of a global lock.
2. **Mask-metadata index coupling** — `validate_cracks` accesses `masks[i]` by iterating `enumerate(crack_metadata_list)`. If Ultralytics reorders results between boxes and masks (rare but version-dependent), or if any filtering happens between `annotate_frame` and `validate_cracks`, the wrong mask is paired with the wrong metadata entry. Pair masks and metadata explicitly by passing them as tuples.
3. **Per-frame import in LetsView `read()`** — `import winsdk.windows.graphics.imaging as imaging` is inside the `read()` method body. Python caches module imports, but the attribute lookup and namespace binding still runs per call. Move the import to module level or cache it in `open()`.
4. **`delete_inspection` does not remove files** — The DELETE endpoint removes the SQLite row but leaves the image, overlay, metadata JSON, and PDF on disk. Over time this orphans files that consume storage with no way to discover them through the UI.
5. **CSV export loads all records into memory** — `get_inspections(page=1, per_page=10000)` fetches up to 10,000 rows into a Python list before writing them to a StringIO buffer. The hard cap means records beyond 10,000 silently vanish from exports.
6. **No CSRF or auth on destructive endpoints** — DELETE and PATCH endpoints accept unauthenticated requests. If the system is ever network-accessible, any browser tab can delete all inspections via cross-origin fetch. Document as a known limitation or add a simple API key.
7. **Capture worker swallows all exceptions silently** — The `_capture_worker` `except Exception` block resets state to monitoring with no logging. Add at minimum a `logging.exception()` call to preserve a traceback for debugging.

## Database lock contention between capture thread and Flask request threads

Every database operation acquires `_DB_LOCK`:

```python
_DB_LOCK = threading.Lock()

def get_inspections(...):
    with _DB_LOCK:
        conn = _get_connection()
        ...

def insert_inspection(data):
    with _DB_LOCK:
        conn = _get_connection()
        ...
```

The capture worker calls `insert_inspection` after encoding the JPEG, generating the PDF, and writing files — a sequence that takes 200-500ms. During this time, any `/api/inspections` or `/api/summary` request from the frontend blocks on `_DB_LOCK`. Since the frontend polls `/capture/status` every 1500ms and `/status` every 1000ms, this creates observable UI stutter during capture events.

SQLite in WAL mode (already enabled via `PRAGMA journal_mode=WAL`) supports concurrent readers with a single writer without external locking. The fix is to remove `_DB_LOCK` and let each thread create its own connection (which `_get_connection()` already does), relying on SQLite's internal busy timeout (already set to 5000ms) for write serialization.

## Mask-metadata positional coupling in crack_validator

`validate_cracks` iterates metadata by index and accesses the corresponding mask:

```python
for i, meta in enumerate(crack_metadata_list):
    ...
    if masks is not None and i < len(masks):
        mask_i = masks[i]
```

In `annotate_frame`, metadata and masks are built in the same loop order over `range(num_instances)`, so they're aligned today. The coupling becomes fragile if any future change filters or sorts `crack_metadata_list` before passing it to `validate_cracks` — the mask indices would no longer match. The `_capture_worker` passes `analysis_metadata` directly from `annotate_frame` without filtering, so the risk is latent rather than active.

## LetsView per-frame import overhead

Inside `LetsViewSource.read()`:

```python
import winsdk.windows.graphics.imaging as imaging

soft_bitmap = imaging.SoftwareBitmap.create_copy_from_surface_async(...)
```

At 8 FPS this executes 480 times per minute. The import should be moved to `open()` and stored as `self._imaging`, or placed at module top level with the same try/except guard used for other winsdk imports.

## File orphaning on inspection deletion

The `app.py` DELETE route calls `delete_inspection` directly without touching the filesystem:

```python
@app.route("/api/inspections/<capture_id>", methods=["DELETE"])
def api_delete_inspection(capture_id):
    deleted = delete_inspection(capture_id)
    ...
```

The image at `captures/images/INSP-00001.jpg`, its overlay, metadata JSON, and PDF report remain on disk forever. The fix is to query the record before deletion, extract `image_path`, `overlay_path`, `metadata_path`, `report_path`, delete the DB row, then attempt `os.unlink()` on each file (ignoring FileNotFoundError).

## Silent exception swallowing in capture worker

```python
def _capture_worker(self, raw_frame, crack_metadata_list):
    try:
        ...
    except Exception:
        with self._lock:
            self._state = "monitoring"
            ...
    finally:
        with self._lock:
            self._capture_in_progress = False
```

If the YOLO model runs out of memory, the weights file is corrupted, or `cv2.imencode` fails on a malformed frame, the system silently returns to monitoring with no record of what happened. `logging.getLogger(__name__).exception("Capture worker failed")` in the except block preserves a traceback without affecting the user.
