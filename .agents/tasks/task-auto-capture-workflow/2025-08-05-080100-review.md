# Auto-capture workflow v2: background thread and rotation fixes

All eight issues from the prior review have been addressed. The capture pipeline now runs in a dedicated background thread (`_capture_worker`), file rotation caps storage at 500 captures, the `possible_crack` intermediate state has been removed, cooldown enforces a 1.0-second minimum, `analysis_complete` holds for 2.0 seconds, and filename parsing uses regex.

Watch for: The YOLO model instance is shared between the detector's main loop and the capture worker thread without synchronization — concurrent `model.predict()` calls on the same `YOLO` object can corrupt internal state (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The capture manager is now a background-threaded state machine. When any detection crosses the confidence threshold, `process_frame` copies the raw frame, sets a `_capture_in_progress` flag, and spawns a daemon thread that performs JPEG encoding, YOLO re-inference, disk writes, and state transitions independently of the detector loop. The live feed is no longer blocked during capture events.

The concurrency fix introduces a new problem: `annotate_frame` (via `get_model`) returns the same cached `YOLO` model object to both threads. PyTorch model inference is not thread-safe when called concurrently on a single model instance. This needs a lock around `model.predict`, or a second model instance for the capture path.

Storage rotation scans `captures/` after each save and deletes the lowest-numbered files when count exceeds `MAX_CAPTURES` (500). The regex-based filename parser handles arbitrary digit counts correctly.

## Concurrent model inference on shared YOLO instance

The detector loop calls `annotate_frame` on every frame at ~8 FPS:

```python
# detector.py _run():
annotated, crack_present, crack_metadata = annotate_frame(
    frame, weights=self._weights, conf=self._conf, imgsz=self._imgsz,
)
```

Simultaneously, the background capture thread calls the same function:

```python
# capture_manager.py _capture_worker():
annotated, crack_present, analysis_metadata = annotate_frame(
    raw_frame, weights=self._weights, conf=self._conf, imgsz=self._imgsz,
)
```

Both resolve to the same `YOLO` model object via `get_model(weights)` and its `_MODEL_CACHE` dict. PyTorch models maintain internal buffers (batch normalization running stats, intermediate activations in hooks, CUDA stream state on GPU) that are not designed for concurrent access from multiple threads. On CPU, this most commonly manifests as occasional garbled predictions or segmentation faults under load; on GPU, it can corrupt the CUDA context entirely.

The simplest fix is a module-level `threading.Lock` in `inference_core.py` that serializes all `model.predict` calls. This means the capture thread will block until the detector's current inference completes (50-200ms), which is acceptable since capture already runs asynchronously and the user never waits on it. Alternatively, the capture manager could instantiate its own private `YOLO(weights)` instance — more memory but zero contention.

## Model cache initialization race

`get_model` is also unsynchronized:

```python
def get_model(weights: str = "best.pt") -> YOLO:
    weights = str(weights)
    if weights not in _MODEL_CACHE:
        _MODEL_CACHE[weights] = YOLO(weights)
    return _MODEL_CACHE[weights]
```

If the detector and capture threads both call `get_model` before the cache is populated (e.g., on first frame when both paths fire simultaneously), both threads could enter the `if` branch and create separate model instances. The dict assignment itself is atomic in CPython (GIL), so one will "win" and the other's model will be garbage collected — no crash, but wasted time loading a 20+ MB model twice. A `threading.Lock` around the cache check-and-populate eliminates this.
