# Auto-capture workflow for crack detection

Adds a two-stage automatic image capture pipeline on top of the existing live YOLO11-seg detection system. When any detection's confidence crosses a configurable threshold (default 0.85), the capture manager freezes the raw frame, saves it as a high-quality JPEG with JSON metadata to `captures/`, re-runs inference on the captured frame for a dedicated analysis, and displays the fixed result in the frontend analysis panel. A cooldown period prevents rapid-fire captures. The frontend gains a threshold slider and status-flow display; the analysis panel now shows captured-image results instead of continuously updating from the live stream.

Watch for: `_trigger_capture` blocks the detector's inference loop for the duration of a full second YOLO inference pass plus disk I/O (confirmed). The `possible_crack` transition at 90% of threshold introduces a dead zone where cracks between 76.5% and 85% confidence oscillate the state machine without producing useful feedback (likely). No file-count or disk-usage limit exists on the `captures/` directory — long-running systems will fill storage indefinitely (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The capture manager is a state machine (`monitoring -> possible_crack -> threshold_reached -> capturing -> analyzing -> analysis_complete -> cooldown`) that runs synchronously inside the detector's frame loop. Because `_trigger_capture` calls `annotate_frame` (a full YOLO inference pass), the live feed frame rate drops to half its normal rate every time a capture fires. This is the gating architectural concern — the capture pipeline needs to run asynchronously or on a separate thread to avoid stalling the live feed.

The 90%-of-threshold "possible_crack" gate is a hysteresis attempt, but it creates an intermediate state visible to the frontend (status flickers to "Detecting...") for cracks that are close but never trigger a capture. If the intent is debouncing, a confirmation-frame-count approach (N consecutive frames above threshold) would be more predictable than a percentage pre-gate.

The frontend replaces `/analysis` polling with `/capture/status` polling. The analysis panel now shows nothing until the first threshold-crossing event — a behavioral change from the prior continuous-analysis display. The threshold slider fires `POST /capture/threshold` on `change` (not `input`), so the backend value updates only when the user releases the slider.

Disk writes to `captures/` have no rotation, size cap, or cleanup mechanism. On a continuously running system monitoring a cracked surface, this will accumulate files without bound.

<summary>Issues (8)</summary>

1. **Capture blocks live feed** — `_trigger_capture` runs a full YOLO inference + disk I/O synchronously inside the detector loop. Move capture work to a separate thread or queue so the live feed isn't stalled.
2. **Unbounded capture storage** — No file-count or disk-usage limit on `captures/`. Add rotation (e.g., keep last N captures) or a max-size check.
3. **Possible-crack dead zone** — The 90%-of-threshold pre-gate (e.g., 76.5% for an 85% threshold) causes UI state flicker for cracks that never reach threshold. Consider a consecutive-frames confirmation instead.
4. **Analysis panel empty until first capture** — Users see "Monitoring..." even when cracks are visible in the live feed but below threshold. Document this behavioral change or show a "below threshold" indicator.
5. **Race in capture-count increment** — `_capture_count` is incremented under lock, but `_save_capture` writes to disk outside the lock. If two near-simultaneous triggers occurred (currently prevented by state gating, but fragile), they could race on file creation.
6. **Cooldown accepts zero** — `set_cooldown` allows `value >= 0`, meaning a cooldown of 0.0 seconds. Combined with a scene consistently above threshold, this creates a tight capture-per-frame loop that would saturate disk I/O.
7. **analysis_complete state invisible to frontend** — The 100ms sleep between `analysis_complete` and `cooldown` is shorter than the 1500ms poll interval, so the frontend almost never observes this state. Increase the hold time or wait for frontend acknowledgement.
8. **Capture count breaks at 10000** — `_scan_existing_captures` parses only characters 6-10 of the filename, so `crack_10000.jpg` is read as "1000". Use a regex or split on `_` and `.` instead.

## Capture blocks the detector frame loop

`CaptureManager._trigger_capture()` is called from `detector.py`'s `_run()` loop via `process_frame()`, and it performs synchronous work:

```python
# Inside _trigger_capture:
annotated, crack_present, analysis_metadata = annotate_frame(
    raw_frame, weights=self._weights, conf=self._conf, imgsz=self._imgsz,
)
# ... then cv2.imencode, file writes, time.sleep(0.1)
```

A single YOLO inference pass takes 50-200ms depending on hardware. Adding JPEG encoding and two file writes (image + JSON), the detector loop is blocked for 100-400ms per capture event. During this time, no new frames are read from the camera, and the MJPEG stream serves stale data.

The `try/except` wrapper in the detector catches exceptions but doesn't prevent the blocking:

```python
try:
    self._capture_manager.process_frame(frame, crack_metadata)
except Exception:
    pass  # Never let capture logic break the live feed
```

This protects against crashes but not against latency. The fix is either offloading `_trigger_capture` to a background thread (passing the raw frame by copy) or using a `threading.Event` + dedicated capture thread that wakes when triggered.

## Unbounded capture storage

`_save_capture` creates files monotonically (`crack_0001.jpg`, `crack_0002.jpg`, ...) with no upper bound. A 960x540 frame at quality 95 is roughly 100-200KB. At one capture per 5-second cooldown in a scene with persistent cracks, that's ~1.5MB/minute or ~2GB/day. On embedded systems or long-running deployments, this will exhaust storage. A simple rotation (delete oldest when count exceeds N, or when total directory size exceeds a configured limit) would prevent this.

## Possible-crack hysteresis creates UI noise

The `_handle_monitoring` method transitions to `possible_crack` when confidence is >= 90% of threshold but below threshold itself:

```python
if max_conf >= threshold * 0.90:
    if max_conf >= threshold:
        self._trigger_capture(raw_frame, crack_metadata_list)
    else:
        self._state = "possible_crack"
```

For the default threshold of 0.85, this means any detection with confidence between 0.765 and 0.849 will flip the state to `possible_crack`, which the frontend displays as "Detecting..." (yellow badge). If the model oscillates around 0.80 confidence frame-to-frame (common with partially-visible cracks), the status badge flickers between "Monitoring" and "Detecting..." every polling cycle without ever producing a capture. A more stable approach would be requiring N consecutive frames above threshold before triggering, which avoids the intermediate state entirely.

## Analysis panel behavioral change

The frontend now polls `/capture/status` and only renders results when `state === "analysis_complete"`:

```javascript
if (state === "analysis_complete" && data.latest_analysis) {
    renderCaptureAnalysis(data.latest_analysis);
} else if (state !== "analysis_complete" && !lastCaptureTimestamp) {
    analysisContent.innerHTML = '<div class="analysis-empty">...Monitoring...</div>';
}
```

If the threshold is set to 0.85 and the model typically detects at 0.60-0.80 confidence, the analysis panel will permanently show "Monitoring..." even though cracks are clearly visible and annotated in the live feed. The feature description indicates this is intentional, but a "crack detected, below threshold" indicator would reduce user confusion.

## State machine timing: analysis_complete is invisible

After storing the analysis results, `_trigger_capture` sleeps for only 100ms before transitioning to cooldown:

```python
with self._lock:
    self._state = "analysis_complete"

time.sleep(0.1)

with self._lock:
    self._state = "cooldown"
    self._cooldown_start = time.monotonic()
```

Since the frontend polls every 1500ms, there's roughly a 93% chance it will miss the `analysis_complete` state entirely and see `cooldown` instead. The frontend handles this correctly (it preserves the last-rendered analysis), but the status flow display will typically jump from "Analyzing..." straight to "Cooldown" from the user's perspective. Hold `analysis_complete` for at least one poll interval or introduce a frontend-acknowledged transition.

## Capture count file-naming breaks at 10000

`_scan_existing_captures` extracts the number from fixed character positions:

```python
num_str = fname[6:10]  # crack_NNNN.jpg
num = int(num_str)
```

This breaks at capture 10000+ (`crack_10000.jpg` extracts "1000", interprets as 1000). The format string `f"crack_{capture_num:04d}.jpg"` pads to 4 digits but doesn't clamp, so after 9999 captures the scan logic loses track of the highest number and may overwrite existing files.
