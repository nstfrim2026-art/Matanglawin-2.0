# Auto-capture workflow v3: thread-safety serialization

The two blocking issues from v2 (concurrent model inference, cache population race) have been resolved by introducing `_MODEL_LOCK = threading.Lock()` in `inference_core.py` and wrapping both `get_model()` cache access and all `model.predict()` calls under that lock. The detector thread and capture background thread now correctly serialize all model access.

Watch for: The threshold slider initializes to 85% in HTML but never syncs with the backend's actual value on page load — if the server restarts with a different default or the threshold was changed in a prior session, the slider shows a stale value (confirmed). The capture's `annotate_frame` call catches all exceptions and falls back to the original metadata list, which means a model failure during analysis silently produces results from the live-detection pass rather than signaling an error to the user (confirmed, but acceptable as a degraded-mode choice).

**Verdict**: APPROVED

## High-level view

The thread-safety fix serializes all model access through a single module-level lock. Both `get_model()` (cache population) and `model.predict()` (in `annotate_frame` and `run_overlay`) acquire `_MODEL_LOCK` before touching the model. The capture thread blocks while the detector thread runs inference and vice versa, adding up to ~100ms of contention per capture event.

The frontend threshold slider is hard-coded to `value="85"` in HTML and never fetches the current backend value on load. If the server's threshold diverges from 85% (through a prior API call or a code change to the default), the slider will be out of sync until the user interacts with it.

## Threshold slider initialization gap

In `templates/dashboard.html`:

```html
<input type="range" id="thresholdSlider" class="threshold-slider"
       min="50" max="100" value="85" step="1">
<span class="threshold-label" id="thresholdLabel">85%</span>
```

The value is always 85 regardless of backend state. In `dashboard.js`, the `pollAnalysis` function already fetches `/capture/status` which returns `threshold` as a float, but the response is never used to update the slider position. Adding a one-time sync on the first successful poll would close this:

```javascript
if (!sliderSynced && data.threshold) {
  thresholdSlider.value = Math.round(data.threshold * 100);
  thresholdLabel.textContent = thresholdSlider.value + "%";
  sliderSynced = true;
}
```

This matters in deployment scenarios where the app restarts and the user refreshes the page — a previously-changed threshold would appear as 85% in the UI while the backend uses the actual configured value.

## Silent analysis fallback

In `capture_manager.py` lines 253-259:

```python
try:
    annotated, crack_present, analysis_metadata = annotate_frame(
        raw_frame, weights=self._weights, conf=self._conf, imgsz=self._imgsz,
    )
except Exception:
    annotated = raw_frame
    crack_present = False
    analysis_metadata = crack_metadata_list
```

When the model fails (out-of-memory, corrupted weights, GPU error), the captured "analysis" is actually the metadata from the prior live-detection pass. This produces correct-looking results that came from a different inference context (possibly a different frame crop due to timing). The metadata dict should include a signal (`"analysis_source": "fallback"` vs `"analysis_source": "dedicated"`) so the frontend or a future audit trail can distinguish dedicated-analysis results from inherited ones.
