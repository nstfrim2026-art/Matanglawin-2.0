# LetsView window capture as a new video source

Adds a screen-capture video source (`LetsViewSource`) that grabs frames from the LetsView mirroring window on Windows, enabling the DJI Fly app to feed into the existing YOLO crack detection pipeline without any camera hardware changes. The implementation follows the existing `VideoSource` interface (open/read/release/is_open), registers itself in the source selector as "DJI Fly (LetsView)", and uses `mss` + `pygetwindow` for fast region capture. On non-Windows platforms the source gracefully refuses to open.

Watch for: No automatic reconnection when the LetsView window disappears mid-session (confirmed) — the detector drops to NO SIGNAL and the user must manually re-select the source. The `read()` method holds a threading lock for the entire duration of the mss capture call, which blocks `is_open` and `release()` during each frame grab (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The capture strategy is region-based (`mss.grab` with the window's bounding box), not window-handle-based. Other windows overlapping LetsView will bleed into the captured frames. On a dedicated detection laptop this is acceptable, but it's a known limitation worth documenting.

The missing reconnection loop is the most impactful gap. The existing detector loop sets `_video_source = None` when `read()` returns failure, then spins showing NO SIGNAL until the user POSTs `/set_source` again. The user requirement explicitly calls for automatic retry every second when LetsView disappears. This isn't implemented.

Each `read()` call holds `self._lock` while performing the mss screenshot, the numpy conversion, and the color-space conversion — roughly 5–15ms of work per frame. During that window, `is_open` and `release()` block. At 25-30 FPS this creates contention if any other thread queries state concurrently.

## Missing reconnection loop

The user requirement specifies "the system should continuously search every second" when LetsView is closed, reconnecting automatically. The current implementation has no such path. When `read()` returns `(False, None)` — signaling the window disappeared — the detector's `_run` loop releases the source, sets `_video_source = None`, and then enters the `if self._video_source is None` branch that shows NO SIGNAL and sleeps 0.5s indefinitely. There is no code that re-attempts `open()` on the current source.

The fix belongs in `detector.py`'s run loop. When `_video_source` drops to None and no new `_pending_source_key` has been set, the loop should re-instantiate the appropriate source and call `open()` again (with a 1-second backoff). This keeps the reconnection logic source-agnostic — it would also help IP cameras that temporarily lose their stream.

## Lock scope in read()

The entire body of `read()` executes under `self._lock`:

```python
def read(self):
    with self._lock:
        if not self._opened:
            return False, None
        # ... window checks ...
        screenshot = self._sct.grab(monitor)  # I/O bound, ~5-15ms
        frame = np.array(screenshot, dtype=np.uint8)  # allocation
        frame = cv2.cvtColor(frame, cv2.COLOR_BGRA2BGR)  # compute
        return True, frame
```

The expensive work — the grab, the array copy, and the color conversion — doesn't need mutual exclusion with the state fields once you've confirmed the source is still open and copied the geometry. A better pattern: acquire the lock, validate state and copy the monitor dict and `_sct` reference, release the lock, then perform the capture and conversion outside the lock. Re-acquire briefly only if you need to update internal state on failure.

## Region capture vs. window capture

`mss` captures a screen region defined by pixel coordinates. It doesn't use the window handle to extract the window's back buffer. If another window partially overlaps LetsView, those pixels appear in the captured frame.

Windows-native alternatives (`PrintWindow` via `pywin32`, or DX-based capture via `dxcam`) capture the window surface directly regardless of occlusion. The task spec mentions `dxcam` as "preferred if available" but the implementation doesn't attempt to use it. For v1, documenting the "keep LetsView in foreground" constraint near the capture call is sufficient.

## Minimized-window status frame runs through inference

When `read()` detects a minimized window, it returns `(True, status_frame)`. The detector loop feeds this to `annotate_frame()`, running YOLO inference on a dark gray placeholder at ~8 FPS. On low-end hardware, the detector could skip inference when it receives a status frame (e.g., check a sentinel or frame dimensions) to avoid wasted cycles.
